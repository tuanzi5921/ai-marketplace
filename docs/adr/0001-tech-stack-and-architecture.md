# ADR-0001: 技术栈与整体架构选型

- **状态**：Accepted
- **日期**：2026-08-27
- **决策来源**：Round 6 访谈结论

## 上下文 (Context)

企业 AI 应用市场是长期运营的内部平台。已完成 6 轮访谈，约束条件如下：

1. **部署**：私有化部署（公司内网/私有云，数据不出公司）
2. **算力**：v1 不需要 GPU（AI 评审默认关闭）
3. **入口**：企微工作台 H5 应用（PC）+ 企微小程序（移动）+ 企微机器人消息推送
4. **后台**：PC 独立运营后台，浏览器访问
5. **存储**：复用企业现有存储（NAS / 已有对象存储）
6. **集成**：企微 SSO、机器人消息、小程序鉴权
7. **认证**：企微 SSO（全员企业内部）
8. **运营人力**：有限，需主流栈降低后续招聘与运维门槛

需要选定一组合适的技术栈作为后续开发与招聘基线。这是承重决策——选定后招聘、组件库、文档、SDK 全部围绕它展开，回退成本极高。

## 决策 (Decision)

采用 **企业级主流栈**：

### 前端
- **用户端 PC**：Vue 3 + TypeScript + Vite + Element Plus（嵌入企微工作台 H5 应用）
- **用户端移动**：企微小程序（与 PC 共享后端 API，独立小程序前端工程）
- **运营后台**：Vue 3 + TypeScript + Vite + Element Plus（PC 独立 H5，浏览器访问）

### 后端
- **框架**：Spring Boot (Java 17)
- **数据库**：MySQL 8 + Redis 7
- **集成**：企微 SDK（SSO、机器人消息推送、小程序鉴权）

### 部署
- **私有化部署**在公司内网，无云端依赖
- **大文件存储**复用企业既有存储（NAS / 对象存储）

## 备选方案 (Alternatives Considered)

### A. 全栈 JavaScript（Vue3 + Nest.js + PostgreSQL）
- 优点：单语言跨端，开发效率高
- 缺点：企业内部 Java 生态更成熟，招聘池更广；后续接入 AI 评审模块时 Nest.js 与 Python 模型生态弱
- **否决**：长期可维护性与招聘难度的权衡更倾向 Java

### B. Python 后端（Vue3 + FastAPI + PostgreSQL）
- 优点：与未来 AI 评审模块同语言，模型接入更顺
- 缺点：v1 不需要 AI 评审（默认关闭），Python 在企业内部 Web 生态弱；现成运维与中间件不如 Java
- **否决**：当前阶段 AI 评审尚未启动，过早为该维度妥协架构主流性不划算；AI 评审模块未来作为独立服务接入即可

### C. Node.js + Express/Koa
- 优点：轻量、上手快
- 缺点：企业级中间件、ORM、监控生态不如 Spring Boot；运维门槛在长期会暴露
- **否决**：长期运营平台不适合轻量栈

## 后果 (Consequences)

### 正面
- 招聘池广：Java + Vue 是国内企业最常见的组合，运营人力门槛低
- 企微 SDK 文档与示例以 Java 居多，集成阻力小
- Spring Boot 生态成熟：审计、监控、ORM、缓存、消息队列等组件齐全
- Element Plus 与 Vue 3 是国内管理后台主流组合，组件库丰富
- 后续 AI 评审模块作为独立 Python 服务接入，对主架构无侵入

### 负面
- 用户端 PC + 用户端移动（小程序）+ 运营后台 = 3 个前端工程，前端工作量大
- 小程序与 H5 不能完全复用 UI，需独立实现两套界面（仅 API 共享）
- AI 评审模块作为独立服务引入，会增加一套部署与运维（仅当开启时）

### 风险与缓解
- **风险**：3 套前端并行开发人力压力
- **缓解**：v1 移动端可考虑先复用 PC 的 H5（嵌入企微移动端也能跑），小程序作为后续迭代；运营后台可缩减组件密度，先做最基础审核流与作品管理
