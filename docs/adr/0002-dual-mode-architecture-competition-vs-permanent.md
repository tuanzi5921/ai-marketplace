# ADR-0002: 双模架构（大赛期 vs 常驻期）

- **状态**：Accepted
- **日期**：2026-08-27
- **决策来源**：Round 7 访谈结论

## 上下文 (Context)

平台定位是长期运营的企业 AI 应用市场，AI 技能大赛作为启动赛事。Round 7 用户明确：

1. **大赛近期启动**：时间紧，v1 必须支持大赛运行
2. **大赛期间**：用户在指定期间内自由上传作品 → 通过审核后发布 → 在大赛指定日期完成最终评审
3. **所有日期必须可配置**：起止日期、评审日期、入围阈值、赛道划分、Top N、奖项设置都由运营在后台配置
4. **常驻运营**：大赛结束后转为日常运营，不再做大赛评定

这意味着平台不能只做"大赛专用"或"日常市场"单一线路，必须支持两种模式：大赛期（含赛事配置、入围、赛道排名、评委评审）与常驻期（日常上传下载、积分兑换）。

## 决策 (Decision)

采用 **双模架构**：单一平台，通过后台配置切换"大赛模式 / 常驻模式"。

### 模式定义

#### 大赛模式 (Competition Mode)
- 时间窗口：运营在后台配置 `大赛起止日期` + `评审日期`
- 上传规则：大赛期间允许自由上传（与常驻期一致，仍走审核 SLA）
- 评定规则：
  - 提交者累计积分过**入围阈值**（配置） → 入围
  - 入围作品按**业务赛道**（配置：如 AI / HR / 财务 / 产研 / 销售 / 运营）分组排名
  - 每赛道取 **Top N**（配置）进入评委评审
  - 评委会现场评审决出**各赛道一/二/三等奖**
- UI 呈现：大赛节点倒计时、赛道榜单、获奖作品特殊标记

#### 常驻模式 (Permanent Mode)
- 时间窗口：大赛结束后或未启动大赛时
- 上传规则：日常上传，走审核 SLA
- 评定规则：无赛事评定；积分用于兑换徽章、奖品
- UI 呈现：常规榜单、积分排行

### 数据模型

```
Competition (赛事实体)
├─ id
├─ name (如 "2026 AI 技能大赛")
├─ status (draft / active / judging / closed)
├─ submit_start_at / submit_end_at (大赛起止日期)
├─ review_at (评审日期)
├─ tracks[] (赛道配置)
├─ shortlist_threshold (入围阈值)
├─ top_n (每赛道入围数)
└─ awards[] (奖项配置)
```

- 一个平台同时只有一个 active 赛事
- 历史赛事 closed 后仍可查询
- 作品与赛事多对多：一个作品可同时参加多个赛事（理论上）

### 配置中心

所有日期、阈值、赛道、奖项由后台**配置中心**管理，运营在 PC 后台修改无需重启服务。

## 备选方案 (Alternatives Considered)

### A. 单赛事专用平台（不做常驻模式）
- 优点：开发量小，UI 简单
- 缺点：与 Round 1 已定的"长期运营"决策冲突；大赛结束后平台无意义
- **否决**：违反基础定位

### B. 双平台分离（大赛专用平台 + 常驻市场平台）
- 优点：每个平台职责单一，互不干扰
- 缺点：双倍开发量；数据迁移复杂；用户、作品、积分要跨平台同步
- **否决**：开发成本不可接受，且 Round 1 已定单一应用市场定位

### C. 单一模式但允许赛事叠加（不做模式切换，仅赛事实体）
- 优点：数据模型最简洁
- 缺点：UI 上需要根据"当前是否在赛事窗口内"动态切换展示逻辑，本质上仍是双模，只是不做模式字段
- **否决**：实际等价于双模，但缺少显式模式字段会让 UI 切换逻辑分散难维护

## 后果 (Consequences)

### 正面
- 单一平台承载双场景，数据贯通：作者、作品、积分、评分在两个模式间无缝复用
- 大赛结束后无需数据迁移，模式切换即可
- 配置中心化，运营自主可控，不依赖开发

### 负面
- 数据模型多一层赛事实体与作品-赛事关联表
- UI 需根据当前模式动态渲染（大赛倒计时、赛道榜单 vs 常规榜单）
- 模式切换点需谨慎设计：切换时进行中作品如何处理？建议只在大赛节点切换，不允许中段切换

### 风险与缓解
- **风险**：模式字段会让 UI 逻辑分支增多，前端复杂度上升
- **缓解**：用统一组件库，按 `mode` props 切换；或用路由分组 `/competition/*` vs `/market/*`
